# BK-667 — Acceptance Criteria

> Jira field: `customfield_10110` · [View in Jira](https://jira.upexgalaxy.com/browse/BK-667)

## AC-01 — Every endpoint BK-037 names requires the key

```
Scenario Outline: A create call without an Idempotency-Key is refused before anything is written
  Given I hold a Personal Access Token that is otherwise allowed to make the call
  When I POST a valid body to <endpoint> with no Idempotency-Key header
  Then the request is refused as a bad request naming the missing header
  And no record is created

  Examples:
    | endpoint                                  |
    | /api/v1/workspaces                        |
    | /api/v1/workspaces/{workspace_id}/projects|
    | /api/v1/modules/{module_id}/user-stories  |
    | /api/v1/atcs                              |
    | /api/v1/bugs                              |
```

```
Scenario Outline: A malformed key is refused as invalid, distinctly from a missing one
  Given I POST a valid body to <endpoint>
  And my Idempotency-Key is "abc" (shorter than the published minimum)
  Then the request is refused as a bad request naming the key as invalid rather than absent
  And no record is created

  Examples:
    | endpoint           |
    | /api/v1/workspaces |
    | /api/v1/atcs       |
    | /api/v1/bugs       |
```

```
Scenario: The accepted key shape is the one the product already publishes
  Given the two endpoints that already require the header accept 8 to 128 characters of letters, digits, underscore and hyphen
  When the five endpoints in this story are checked against that same shape
  Then all seven accept and reject exactly the same keys
  And a value generated by the browser's random UUID helper is accepted by every one of them
```

## AC-02 — A retry returns the first answer and writes nothing twice

```
Scenario Outline: The same key with the same payload replays the stored response
  Given I POST a valid body to <endpoint> with key "K" and receive a success
  When I POST the identical body to the same endpoint with key "K" again
  Then I receive the same response body and the same status code as the first call
  And exactly one record exists for that payload

  Examples:
    | endpoint                                  |
    | /api/v1/workspaces                        |
    | /api/v1/workspaces/{workspace_id}/projects|
    | /api/v1/modules/{module_id}/user-stories  |
    | /api/v1/atcs                              |
    | /api/v1/bugs                              |
```

```
Scenario: Property order in the payload does not defeat the replay
  Given I create an ATC with key "K" and a body whose properties are in one order
  When I resend the same values with the properties in a different order under key "K"
  Then it is treated as the same request and replayed
  And no second ATC is created
```

```
Scenario: A replay outside the window is a new request
  Given I created a Bug with key "K" more than the stored window ago
  When I POST the same body with key "K"
  Then a new Bug is created
  And this matches the window the two already-shipped endpoints honour
```

## AC-03 — Reuse and races are refused, not served

```
Scenario Outline: The same key with a different payload is a conflict
  Given I POST a valid body to <endpoint> with key "K" and receive a success
  When I POST a different body to the same endpoint with key "K"
  Then the request is refused as a conflict
  And the second body is not written

  Examples:
    | endpoint           |
    | /api/v1/workspaces |
    | /api/v1/atcs       |
    | /api/v1/bugs       |
```

```
Scenario: A second call arriving while the first is still in flight is a conflict
  Given a create call with key "K" has started and has not yet answered
  When a second call with key "K" and the same payload arrives
  Then the second call is refused as a conflict rather than allowed to write concurrently
  And exactly one record exists once the first call completes
```

```
Scenario: Two different callers may reuse the same key text without colliding
  Given two members of different Workspaces each POST to /api/v1/atcs with the key "shared-key-value"
  When both requests are processed
  Then both succeed
  And each caller receives their own ATC
```

```
Scenario: One caller may reuse a key across two different endpoints
  Given I POST to /api/v1/workspaces with key "K" and it succeeds
  When I POST to /api/v1/atcs with the same key "K" and an unrelated valid body
  Then the second call is not treated as a replay of the first
  And it creates the ATC
```

## AC-04 — A failure before the write does not strand the key

```
Scenario: A validation failure leaves the key reusable
  Given I POST an invalid body to /api/v1/atcs with key "K"
  And the request is refused for that invalid body
  When I POST a corrected body with a fresh key
  Then the ATC is created
  And the earlier key does not block any later honest attempt
```

```
Scenario: A record that was written stays written even if the response could not be stored
  Given a create succeeds but the stored-response snapshot cannot be saved
  Then the caller still receives the success answer for the record that exists
  And a later retry with the same key does not mint a second record
```

## AC-05 — Every in-product caller sends a key

```
Scenario Outline: Each screen that creates one of these records supplies a key
  Given I am signed in with a browser session
  When I submit <form>
  Then the request carries an Idempotency-Key
  And the record is created exactly as it was before this story

  Examples:
    | form                                                     |
    | the onboarding form that creates my first Workspace      |
    | the create-project form                                  |
    | the user-story form, on its create path                  |
    | the new-ATC editor                                       |
    | the file-a-Bug dialog                                    |
```

```
Scenario: Double-submitting a form creates one record, not two
  Given I am on the create-project form with a valid name
  When I trigger submit twice before the first answer arrives
  Then exactly one Project is created
  And I am not shown a conflict error for my own double-click
```

```
Scenario: A refused submit rotates the key before the next attempt
  Given my first submit was refused because the name was already taken
  When I correct the name and submit again
  Then the second submit carries a different key from the first
  And it succeeds rather than being refused as a payload mismatch
```

```
Scenario: Editing is not turned into a create
  Given the user-story form is open on an existing User Story
  When I save my edit
  Then the edit behaves exactly as it did before this story
  And nothing about the edit path is refused for a missing key
```

## AC-06 — New-user onboarding still works end to end

```
Scenario: A brand-new account reaches a usable product
  Given I have just confirmed a brand-new account and have no Workspace
  When I complete the onboarding form
  Then my Workspace is created
  And I land in the product signed in, with no error and no refused request
```

```
Scenario: An agent bootstrapping with a fresh token can still create its first Workspace
  Given I hold a newly minted Personal Access Token and belong to no Workspace
  When I create a Workspace over the API supplying an Idempotency-Key
  Then the Workspace is created
  And the headless bootstrap path documented for QA still works as documented
```

Scenario: The cross-cutting requirement no longer contradicts the shipped routes
  Given BK-037 currently calls the header optional and caps it at 64 characters

  Then it describes the header as required on every endpoint it names
  And it states the key shape the shipped helper actually enforces
```

```
Scenario: The API map and the QA testability guide agree with the routes

  And the QA testability guide documents the Workspace-create call an agent uses to bootstrap

  And the QA guide tells a tester that the call needs an Idempotency-Key

## AC-09 — Idempotency key must not leak across Workspaces (NEEDS PO/DEV CONFIRMATION)

> Added by Shift-Left refinement, 2026-09-12. Behavior inferred from `lib/api/idempotency.ts` (lookup key = `user*id, endpoint, key`, no `workspace*id`) — see Critical Question for PO in the ATP. Not yet confirmed by PO/Dev.

```
Scenario: Should scope the idempotency key per Workspace, not only per caller and endpoint
  Given I am a member of Workspace A and Workspace B
  And I POST to /api/v1/atcs in Workspace A with key "K" and an ATC body, and it succeeds
  When I POST to /api/v1/atcs in Workspace B with the same key "K" and an identically-shaped body
  Then the second call is treated as a genuine new request scoped to Workspace B
  And an ATC is created in Workspace B, never replayed from Workspace A's stored response
```
