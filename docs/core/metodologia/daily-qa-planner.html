Planificación diaria de QA con daily-qa-planner

Una rutina para convertir tickets y documentos del equipo en una cola diaria de pruebas priorizada, trazable y lista para revisar, sin mezclar proyectos ni escribir en el TMS por defecto.

Preparación por proyecto

Instala la skill por separado en cada repositorio que quieras planificar. Así las fuentes, las instrucciones del equipo y el archivo de sesión permanecen dentro del proyecto correcto.

  1. Copia la carpeta de la skill

    Copia .agents/skills/daily-qa-planner/ completa, incluidos references/daily-plan-template.md y evals/evals.json, a la misma ruta en el proyecto destino.

  2. Configura la activación del proyecto

    En .agents/instructions/agent-project.md, añade triggers en el frontmatter y una fila en la tabla Project context skills. Usa expresiones adecuadas al idioma del equipo y confirma que la fila apunta a .agents/skills/daily-qa-planner/SKILL.md.

  3. Comprueba los flujos disponibles

    Si el proyecto también tiene shift-left-testing, sprint-testing o test-documentation, el planner puede recomendarlos. Si no están, seguirá preparando el plan y señalará que no hay una skill downstream disponible.

  4. Haz una prueba pequeña

    Pásale una historia y una lista corta del equipo. Revisa que las referencias apunten a las fuentes correctas y que el informe se guarde en .session/daily-qa-planner/YYYY-MM-DD/daily-plan.md dentro de ese repositorio.

No copies el boilerplate entero

Para reutilizar el planificador basta con la carpeta de la skill y la activación local. Conserva solo las integraciones que el proyecto realmente tenga; la skill no requiere parsers propios ni dependencias de Excel/PDF.

Rutina diaria en siete pasos

  1. Abre el repositorio correcto

    Trabaja desde el checkout del proyecto que vas a probar. No combines adjuntos ni tickets de productos distintos en una misma sesión.

  2. Reúne las fuentes del día

    Puedes adjuntar Excel, CSV, PDF, documentos o texto; proporcionar claves de Jira/Xray; o entregar ambas fuentes juntas. Indica fecha, sprint, release o módulo si acota el trabajo.

  3. Describe la prioridad y las restricciones

    Por ejemplo: bloqueo de release, retest urgente, dependencias conocidas o tiempo disponible. No hace falta inventar una prioridad numérica; el planner conserva las prioridades de origen y explica el orden sugerido.

  4. Pide el plan diario

    Solicita una cola priorizada con objetivo, escenarios de prueba, riesgo, dependencias, fuentes y nivel de confianza para cada tarea.

  5. Revisa referencias y dudas

    Comprueba las claves y secciones citadas. Resuelve conflictos que puedan cambiar el comportamiento esperado; las asociaciones basadas solo en título o módulo deben aparecer como tentativas.

  6. Elige qué ejecutar

    Confirma la cola y abre manualmente la skill recomendada para cada ticket o grupo de trabajo. El planner no inicia esas skills ni ejecuta pruebas por sí solo.

  7. Conserva el resultado del día

    El informe queda en .session/daily-qa-planner/YYYY-MM-DD/daily-plan.md. Puedes usarlo como registro de trabajo y volver a la sesión si necesitas reanudarla.

Prompts para empezar

Situación Ejemplo Qué debe producir
Excel y tickets “Organiza mi jornada de QA. Adjunto un Excel con tareas para PROJ-123 y PROJ-124; consulta esos tickets y prepara el orden y los escenarios.” Plan priorizado con referencias a ambos orígenes y diferencias visibles.
Documentos sin tickets “Con este PDF y la hoja del equipo, arma mi plan diario. Algunas tareas no tienen clave de Jira.” Tareas sin ticket marcadas como tales; sin claves ni responsables inventados.
Ticket para ejecución “Prueba PROJ-123 de punta a punta y confirma si el arreglo funciona.” Derivación a sprint-testing; no afirma que la prueba ya se ejecutó.
Lista de sprint “Planifica mi QA para el sprint 14. Usa esta lista de tickets y este PDF con los riesgos del equipo. Marca bloqueos y no actualices Jira.” Cola ordenada, riesgos respaldados por el PDF y ninguna escritura externa.

Cómo leer el plan

El archivo daily-plan.md separa las recomendaciones de los datos originales:

  • Orden: recomendación del planner basada en instrucciones explícitas, preparación, dependencias e impacto/riesgo; no cambia la prioridad del ticket.
  • Confianza alta/media/baja: cuánto respaldo tienen las referencias y la relación entre fuentes, no una probabilidad matemática de que una prueba falle.
  • Coincidencia confirmada: vínculo o clave exacta. Tentativa: semejanza por título, equipo o módulo que debes verificar.
  • Preguntas abiertas: datos faltantes que pueden cambiar cobertura, resultado esperado o siguiente acción.
  • Escrituras externas: debe decir ninguna salvo que una acción se haya aprobado y verificado por separado.

Elegir el siguiente flujo QA

Situación Skill sugerida Qué ocurre después
Historia en backlog; ACs requieren refinamiento antes del sprint shift-left-testing Refina requisitos y deja outlines pre-sprint; no ejecuta pruebas.
Ticket listo para QA, retest o exploración en sprint sprint-testing Planifica, ejecuta y reporta el QA del ticket.
Comportamiento ya validado que debe formalizarse en el TMS test-documentation Prioriza y documenta casos ya validados.
Proyecto destino sin la skill correspondiente Sin derivación Usa el plan como borrador y registra la capacidad faltante.

Para iniciar el siguiente flujo, invoca la skill sugerida con su ticket/alcance. La aprobación de este plan no autoriza cambios en Jira/Xray: para crear o actualizar elementos, aprueba por separado los elementos, campos y vínculos propuestos.

Trabajar con varios proyectos

  1. Abre un checkout y una sesión por proyecto.
  2. Adjunta solo archivos de ese proyecto y usa sus propias claves de ticket.
  3. Guarda cada informe dentro de .session/ de ese repositorio.
  4. Si una tarea afecta dos productos, sepárala o indícalo explícitamente; no dejes que una coincidencia de nombres fusione los tickets.

La skill es portable, pero la configuración y las fuentes no lo son: cada proyecto necesita su propia fila de activación y sus propios documentos/tickets. No copies cachés Jira, .env, credenciales ni archivos de sesión entre repositorios.

Límites y problemas comunes

  • Un PDF escaneado, protegido o ilegible requiere una exportación accesible o el fragmento pertinente. El planner no incluye OCR propio.
  • Si Jira no está disponible, puedes entregar un export; el plan debe identificarlo como snapshot y no como estado en vivo.
  • Si ticket y documento discrepan, revisa ambas referencias antes de aceptar cobertura o comportamiento esperado.
  • El planificador no asigna testers, no ejecuta pruebas, no crea bugs/tests y no modifica Jira/Xray por defecto.
